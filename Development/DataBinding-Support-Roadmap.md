# Data Binding 支持路线图

## 目标

MarkupUI 数据绑定需要在 UObject 与 RML 页面之间形成可验证的双向通路：页面能够读取并跟随业务数据变化，允许写入的控件能够安全地把值写回业务对象，同一个对象被多个页面观察时保持一致。

集合结构变化不属于普通标量写回。Array 和 Map 由业务代码或页面命令修改，再通过集合通知报告变化。

## 当前结论

UObject 已经具备双向数据绑定的底层读写通路，但属性访问权限、访问器调用、跨 Context 同步和端到端验证尚未闭环。因此当前状态不能标记为“完整支持 UObject 双向数据绑定”。

## 当前支持情况

| 能力 | 状态 | 当前范围 |
| --- | --- | --- |
| UObject 设置为具名数据上下文 | ✅ 已具备 | 同名上下文可以设置、替换和移除。 |
| UObject → RML 初次读取 | ✅ 已具备 | 支持已公开给绑定系统的标量、UObject、USTRUCT、Array 和 Map。 |
| 多级属性路径读取 | ✅ 已具备 | 支持对象、结构和数组组成的已访问路径；Map 页面语法仍按独立计划处理。 |
| UObject 属性变化 → RML | ✅ 已具备 | 普通属性通知会在下一次页面更新前自动合并。 |
| Array/Map 结构变化 → RML | ✅ 已具备 | 通知保留操作种类、索引、数量和 Map Key，具体前端决定最终刷新粒度。 |
| RML → UObject 标量写回 | ⚠️ 基础通路已具备 | `data-value` 和 `data-checked` 可以把兼容标量写回反射属性。 |
| 当前 RML 模型在写回后刷新 | ✅ 已具备 | 成功写回后，RmlUi 会重新求值相关顶层变量。 |
| Blueprint 只读/可写权限 | ❌ 未闭环 | 写回入口尚未完整执行属性的只读约束。 |
| Blueprint Getter/Setter | ❌ 未闭环 | 绑定读写尚未保证经过属性声明的 Getter 和 Setter。 |
| Setter 校验和修正 | ❌ 未闭环 | 写回可能绕过业务校验、钳制和联动逻辑。 |
| 同一 UObject 的多 Context 同步 | ❌ 未闭环 | 一个页面写回后，其他观察同一对象的页面尚未保证收到变化通知。 |
| 页面直接修改 Array/Map 结构 | ➖ 不计划支持 | 使用页面命令表达新增、删除和替换意图。 |
| 完整端到端自动化验证 | ❌ 未完成 | 已有底层读取与写入测试，但缺少真实控件事件覆盖。 |

## 双向绑定完成标准

只有同时满足以下条件，才能将 UObject 双向绑定标记为完成：

1. 页面只能写入明确允许写入的属性。
2. 只读属性的写回请求被拒绝，且不会改变对象。
3. 声明了 Getter 或 Setter 的属性必须经过对应访问器。
4. Setter 可以接受、拒绝或修正输入，页面最终以业务对象中的实际值为准。
5. 写回成功后，所有观察同一 UObject 的有效 Context 都能同步。
6. 失败写入不会留下页面值与业务值长期不一致的状态。
7. 支持类型、转换规则和失败日志与公开契约一致。
8. 自动化测试覆盖真实 RML 控件事件，而不仅是直接调用内部读写接口。

## 实施任务

### 阶段 1：属性访问契约

- [ ] 为反射标量建立明确的可读、可写能力判断。
- [ ] 对只读属性拒绝 RML 写回。
- [ ] 保持只写属性不能作为 `data-value` 或 `data-checked` 目标，因为这两种绑定需要读取当前值。
- [ ] 记录并报告因访问权限不匹配而失败的绑定请求，避免重复刷屏。

完成条件：只读、读写和不可绑定属性的行为均可预测，写回不会绕过声明的访问权限。

### 阶段 2：Getter 与 Setter

- [ ] 属性声明 Getter 时，通过 Getter 读取当前值。
- [ ] 属性声明 Setter 时，通过 Setter 写回页面值。
- [ ] 没有自定义访问器时，才直接访问允许读写的反射属性。
- [ ] Setter 执行后重新读取最终值，支持范围钳制、标准化和业务修正。
- [ ] Setter 拒绝或无法完成写入时，保持原业务值并恢复页面显示。

完成条件：页面写入与游戏代码调用同一业务入口，Setter 中的校验和联动逻辑不会被绕过。

### 阶段 3：写回通知闭环

- [ ] 标量写回成功后发送对应 UObject 属性变化通知。
- [ ] 同一个 UObject 被多个模型或多个 Context 观察时，所有有效观察者都收到更新。
- [ ] 当前发起写回的 RML 模型与外部通知自动合并，避免重复更新循环。
- [ ] 嵌套 UObject 属性写回时，从实际拥有该属性的对象发送本地属性通知。
- [ ] 对象、Context 或文档已经失效时安全跳过通知。

完成条件：任一页面或业务代码修改对象后，所有观察该对象的页面在下一次更新中显示同一个最终值。

### 阶段 4：类型与错误处理

- [ ] 核对 Bool、Int32、Int64、Float、Double、String、Text、Name、Enum、Color 和 Vector2D 的读写行为。
- [ ] 明确数字转换、枚举合法性和字符串转换规则。
- [ ] 类型不匹配、属性失效、对象失效和 Setter 拒绝均返回失败。
- [ ] 错误日志包含模型名、属性路径、请求类型和目标类型，并对相同错误抑制刷屏。
- [ ] 写回失败后重新读取模型值，避免控件暂时保留未接受的输入。

完成条件：所有公开支持类型都有稳定、可诊断且经过测试的成功与失败行为。

### 阶段 5：端到端自动化测试

- [ ] `data-value` 覆盖文本、整数、浮点数和枚举的正常写回。
- [ ] `data-checked` 覆盖 checkbox 与 radio 的布尔写回。
- [ ] 覆盖只读属性拒绝写回。
- [ ] 覆盖 Setter 接受、钳制、修正和拒绝输入。
- [ ] 覆盖嵌套 UObject 属性写回。
- [ ] 覆盖同一 UObject 同时绑定到多个 Context。
- [ ] 覆盖写回后其他只读表达式同步刷新。
- [ ] 覆盖对象、文档和 Widget 销毁后的在途通知安全性。
- [ ] Array 和 Map 通知覆盖新增、追加、插入、删除、替换与整体变化。

完成条件：测试通过真实 RML 文档和控件 `change` 事件验证完整链路，不以直接调用标量 Adapter 作为最终验收。
